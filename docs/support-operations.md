# 운영 문의 처리 절차

이 문서는 현재 구현된 KU Settle의 운영 문의(`support_tickets`) 흐름만 설명합니다. 운영자 연락처, 응답 기한, 외부 업체 전달 여부는 별도 정책이 확정되기 전까지 정하지 않습니다.

## 1. 접수와 사용자 확인

1. 사용자가 **운영 문의**에서 제목과 내용을 제출합니다.
2. 서버가 현재 익명 세션의 `session_id`와 접수번호(`reference_code`)를 함께 저장하고 초기 상태를 `reviewing`으로 기록합니다.
3. 사용자는 같은 브라우저 세션에서 문의 내역, 상태, 운영자 답변을 다시 조회할 수 있습니다. 계정 연결을 완료한 경우에만 계정 복구 범위에 포함됩니다.
4. 조회 중에는 로딩 상태, 성공했지만 내역이 없을 때는 빈 상태, 조회 실패 때는 오류와 재시도 버튼이 표시됩니다. 접수 실패를 성공으로 표시하지 않습니다.

## 2. 운영자 처리

1. 운영자는 관리자 화면에서 관리자 토큰으로 세션을 시작합니다. 토큰은 브라우저 저장소에 저장하지 않으며 서버의 HttpOnly 세션 쿠키만 사용합니다.
2. 문의 탭에서 접수번호·제목·내용·현재 상태를 확인합니다.
3. 답변을 입력하고 상태를 `open`, `reviewing`, `resolved`, `closed` 중 하나로 저장합니다. 삭제가 필요한 경우에도 소프트 삭제(`deleted`)만 사용합니다.
4. 서버는 버전 값을 확인해 다른 운영자의 동시 수정을 거부(`version_conflict`)하고, 변경자·처리 시각·감사 로그를 기록합니다.
5. 저장 요청이 성공해도 후속 재조회가 실패하면 화면에 저장 완료를 표시하지 않습니다. 관리자 화면의 새로고침으로 다시 확인합니다.

## 3. 권한과 데이터 경계

- 일반 사용자 API는 현재 세션의 `session_id`로 필터링되어 다른 세션의 문의를 조회할 수 없습니다.
- 관리자 목록·수정 API는 `requireAdmin` 검사를 통과한 요청만 허용합니다.
- 운영자 답변과 내부 처리 정보는 일반 사용자 응답에 필요한 필드만 노출합니다.
- 실제 데이터로 권한·답변 흐름을 시험하지 않습니다. 격리된 테스트 프로젝트와 테스트 계정이 준비된 경우에만 통합 검증을 수행합니다.

## 4. 정책 미확정과 기능 오류 구분

- **정책 미확정:** 운영자 연락처, 첫 답변 목표 시간, 업무일 정의, 외부 업체 전달 및 실제 서비스 책임 범위.
- **기능으로 구현된 범위:** 문의 저장, 접수번호 발급, 상태·답변 조회, 관리자 상태·답변 수정, 사용자 세션별 격리, 재조회 실패 시 성공 표시 억제.
- **이번 범위 밖:** 업체 예약·결제·실제 배송·보관 연동.

운영 시작 전 정책 미확정 항목을 담당자가 검토·승인하고, 그 결과를 별도 운영 문서와 화면 문구에 반영해야 합니다.

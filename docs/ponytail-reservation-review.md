## 호출과 실제 사용

프로젝트 스킬을 탐색한 새 대화에서는 다음처럼 명시적으로 요청한다. 플러그인 설치가 아니므로 플러그인 네임스페이스 명령과 구분한다.

```text
$ponytail-review 예약 확정 처리 변경과 직접 연결된 호출·테스트만 읽기 전용으로 검토해.
리뷰와 문서는 한국어로 작성해. 정확성, 데이터 보호, 오류 처리, 테스트를 줄 수 절감보다 우선해.
기존 AGENTS.md와 설치된 Next.js 문서 지침을 유지하고 실제 DB 검증과 모의 검증을 구분해.
```

이번 작업에서는 설치 직후 `SKILL.md` 전문을 직접 읽고, 변경분·호출부·관련 서버 경로·테스트·README를 대조하는 방식으로 명시적으로 적용했다. 설치만 했다고 사용 완료로 기록한 것이 아니다. 새 대화의 자동 탐색 UI 자체는 이번 검증 대상이 아니다. 원본의 영어 출력 요구보다 사용자가 지정한 한국어 출력 요구를 우선했다.

## 검토 대상과 가정

여러 사용자가 같은 상품에 동시에 요청할 수 있는 웹 서비스로 보았다. `completeMarketplaceReservation`, 일정 수정·취소, 서버 요청 어댑터, 현재 구매 세션의 재조회, 중복 요청 처리와 상품 상세 갱신 경로를 검토했다. 계정 인증, 이메일 제공자 설정, 익명·인증 테이블 통합, DB 스키마 변경은 제외했다.

## 발견한 문제와 조치

1. **서버 응답 전 예약 확정과 성공 안내**
   - 문제: 요청 실패 후에도 임시 ID와 활성 예약 표시가 남았다. 일정 수정도 생성 경로를 호출했다.
   - 조치: 서버 상품은 유효한 응답의 서버 ID·상품 ID·상태·시간을 확인한 뒤 반영한다. 일정 수정은 기존 예약 ID의 `PATCH`, 취소도 응답 확인 후 반영하도록 바꿨다.
   - 미조치 위험: 저장되지 않은 예약을 확정으로 오해하거나 수정이 새 예약 요청이 될 수 있었다.

2. **응답 유실과 확정 거절의 혼동**
   - 문제: 서버가 저장한 뒤 응답만 유실되어도 실패로 단정할 수 있었다.
   - 조치: 네트워크 오류·타임아웃·5xx는 확인 필요로 남긴다. 현재 구매 세션에 한정한 조회 후 같은 요청 키로 재시도한다. 재조회 실패도 성공으로 표시하지 않는다. 취소 확인 버튼은 모달 위에서 접근 가능하게 배치했다.
   - 미조치 위험: 사용자가 중복 생성 요청을 보내거나 실제 처리 상태와 다른 화면을 볼 수 있었다.

3. **재전송 결과와 로컬 병합의 경계 사례**
   - 문제: 취소·만료 응답을 활성으로 처리하거나, 오래된 취소 결과가 같은 상품의 다른 활성 기록을 지울 수 있었다. 두 조회 사이 다른 요청이 저장되면 같은 요청을 거절로 오인할 수 있었다.
   - 조치: 비활성 상태는 활성화하지 않고 다른 활성 기록은 보존한다. 기존 결과 조회·동시 insert 충돌·상품 상태 변경 경합에서 같은 세션·키·상품·일정의 결과를 확인한다. 상품 상태 반영 실패 시 저장한 예약을 삭제하지 않고 502로 보류하며 같은 키 재시도로 확인한다.
   - 미조치 위험: 중복 시도, 잘못된 확정 표시, 로컬 기록 손실로 이어질 수 있었다.

4. **연결된 상품 소유권과 상세 닫기 회귀**
   - 문제: 익명 사용자가 타인의 서버 상품도 자기 상품으로 판정해 예약 버튼을 볼 수 없었다. 예약 갱신 직후 닫은 상세가 이미 예약된 화면 갱신 프레임에서 다시 열릴 수도 있었다.
   - 조치: 서버 상품은 `ownedByCurrentUser`를 따르고, 지연 프레임 실행 시 현재 `listing` URL이 여전히 일치할 때만 상세를 갱신한다. 샘플 상품의 실제 예약 제한은 유지했다.
   - 미조치 위험: 구매자 경로를 이용하지 못하거나 닫은 화면이 다시 나타날 수 있었다.

## 판정과 검증 한계

예약 확정 표시와 실패·복구 경로의 변경 및 재리뷰를 완료했다. 구체적인 실행 명령과 실제 결과는 [README 검증 기록](../README.md#예약-확정-처리-보완--2026-11-08)에 기록한다.

단위 테스트의 모의 HTTP, Route Handler의 메모리 저장소 대역, Chromium의 모의 API 검증은 실제 Supabase 통합 검증이 아니다. 이 도구의 사용만으로 성능·보안 개선 효과를 보장하지 않는다.

로컬 앱의 격리 확인 엔드포인트는 HTTP 200과 지정한 테스트 프로젝트 일치를 반환했다. 그러나 해당 Supabase 호스트 DNS 조회가 `ENOTFOUND`로 실패했다. 따라서 실제 DB 생성·재전송·동시성·수정·취소·새로고침 복구 검증은 미실행이다. 테스트 데이터는 서버에 생성하지 않았으므로 정리할 행도 없다. 운영 DB로 대체하지 않았다.

예약 생성과 상품 상태 변경은 여전히 별도 DB 쓰기다. 기존 고유 제약과 확인·재시도 경로를 이용하지만, 다중 프로세스 경쟁과 장애 후 복구를 실제 DB에서 통과했다고 주장하지 않는다. 테스트 프로젝트의 접근이 복구된 뒤 별도 검증이 필요하다. 인증 설정, 운영 환경변수, DB 스키마는 이번 작업에서 변경하지 않았다.

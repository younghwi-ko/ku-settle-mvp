### 실제 핸들러와 모의 저장소

- 내부 관리자 메모·담당자·취소 사유·삭제 메타데이터를 채운 행으로 생성, 갱신, 동일 요청 반환, 중복 키 반환, 네 가지 취소 진입 경로의 실제 핸들러 응답을 검사했다.
- 견적 변경·null·누락 입력에도 운영 견적이 유지되고 사용자 입력 변경은 반영되는지 확인했다. 관리자의 견적·내부 메모 갱신과 비관리자 거부도 검사했다.
- 정상 세션, 쿠키 없음, 조회 성공 후 없음, 폐기된 세션, 조회 오류 응답, 조회 예외를 구분했다. 조회 실패 시 새 INSERT·쿠키 교체·last_seen 갱신이 모두 0이고 bootstrap·공통 API·직접 세션 호출 API가 503인지 확인했다.
- 이 검증은 실제 TS 함수와 Route Handler를 실행하지만 Supabase DB·쿠키 저장소·관리자 인증 경계는 대역이다. 실제 RLS·관리자 토큰·DB 잠금 검증은 아니다.

### 로컬 HTTP와 실제 러너 프로세스

- 잘못된 ref, `isolated:false`, 실패 응답, 잘못된 JSON, 동일 origin 리디렉션, 다른 origin 리디렉션을 검사했다. 매번 canonical 환경 확인 GET **한 건만** 발생했고 종료 코드 2였다.
- preflight의 Origin이 대상 origin인지 확인하고 Authorization·Cookie가 없으며 토큰이 출력되지 않는지 검사했다. 리디렉션 대상에도 요청이 없었다.
- 정상 확인의 양성 대조는 환경 확인 뒤에만 대역 페이지가 열리는지 검사한다. 이후 지원 API 대역을 의도적으로 503으로 만들어 실제 데이터 변경 전에 러너가 실패 종료하도록 했다. 이 의도된 자식 프로세스 종료 코드 1은 전체 DB 통합 테스트 성공이 아니다.
- 테스트 대역 페이지의 문자 인코딩 누락으로 양성 대조가 한 차례 타임아웃됐다. 대역 응답에 UTF-8을 명시한 뒤 최종 7개 안전성 검증이 모두 통과했다. 서비스 화면을 고쳐 통과시킨 것이 아니다.

## Ponytail 재리뷰와 남은 범위

`ponytail full`로 기존 공개 필드·오류 전달·러너 흐름을 재사용하고, `ponytail-review`로 변경분과 연결된 호출을 대조했다. 여러 사용자와 운영자가 동시에 접근하는 환경을 전제로 검토했다. 공개 응답에서 내부 필드가 빠지는지, 관리자 경로가 보존되는지, 세션 실패가 기존 쿠키를 덮지 않는지, 격리 확인 실패에서 cleanup까지 진입하지 않는지 확인했고 이번 범위에 추가 수정이 필요한 문제는 발견하지 못했다.

실제 DB 격리·연결은 이번에 확인하지 않아 DB 통합 러너를 실제 Supabase에 실행하지 않았다. 운영 API 쓰기·실제 상품/예약/문의 생성·이메일 발송은 하지 않았다. 새 clone용 예시는 빈 비밀값과 허용된 로컬 기본값인지 검사했고 실제 환경변수 파일은 추적하지 않는다.

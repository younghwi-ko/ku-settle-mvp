## 원인과 최소 수정

기존에는 예약 UPDATE와 상품 UPDATE가 각각 다른 요청이었다. 예약 종료 후 상품 갱신 실패를 롤백할 수 없었고, 이미 종료된 R1의 관리자 정리가 현재 활성 R2의 상품을 `active`로 바꿀 수도 있었다.

기존 테이블과 활성 예약 부분 고유 인덱스를 유지하고 [추가 마이그레이션](../supabase/migrations/202611100001_atomic_guest_reservations.sql)에 RPC 두 개를 준비했다.

| 경로 | 변경 |
| --- | --- |
| 예약 생성·같은 키 재전송 | `create_guest_reservation`: 상품 행 잠금 → 기존 요청 확인/생성 → 상품 예약 상태 갱신을 한 트랜잭션으로 처리 |
| 사용자 취소 | API의 origin·현재 세션·구매자/판매자 검사를 유지하고 `transition_guest_reservation`에 현재 version·세션을 전달 |
| 관리자 종료·soft-delete | `requireAdmin`·origin·version 검사를 유지. 상태 전이 규칙도 RPC에서 다시 확인. 기존 감사 로그 경로 유지 |
| 지연 만료 | 같은 종료 RPC 사용. 실패·version 충돌이면 다음 조회에서 재시도하고 성공 알림을 보내지 않음 |

모든 RPC는 **상품 → 예약** 순서로 잠근다. 다른 요청은 같은 상품의 잠금이 해제된 후 최신 상태를 확인한다. 새 예약의 고유 인덱스도 그대로 남는다. 실제 활성 예약을 종료했고 다른 활성 예약이 없을 때만 `reserved` 상품을 해제/판매 완료 처리한다. 이미 종료된 R1 정리는 상품에 쓰지 않으며 `sold`·`hidden`·`deleted`도 덮어쓰지 않는다. 상품을 변경하면 version도 증가시켜 기존 편집 충돌 검사가 오래된 상태를 감지할 수 있게 했다.

RPC는 `SECURITY INVOKER`다. `PUBLIC`·`anon`·`authenticated`의 실행 권한을 명시적으로 회수하고 `service_role`에만 부여했다. `p_mode=admin`은 신뢰된 서버가 관리자 인증 후 지정하는 인자이며, 공개 사용자가 직접 실행할 수 있는 관리자 인증 수단이 아니다. SQL의 사용자 모드에서도 구매자/판매자와 폐기 세션을 검사한다. 권한을 낮추거나 새 인증 경로를 만들지 않았다.

일정 수정은 기존 구매자·활성 상태·version 조건부 UPDATE를 유지한다. 알림·관리자 감사 로그는 기존처럼 예약 트랜잭션 이후 별도 저장이며, 이 둘까지 원자적으로 저장하는 기능을 추가하지 않았다.

## 실제 DB 검증 실행 방법

개발 의존성 `pg`는 서로 다른 실제 PostgreSQL 연결의 잠금·롤백을 검사하기 위해 추가했다. 서비스 런타임에서는 사용하지 않는다. Docker는 필요하지 않다.

`.env.local`에 기존 격리 URL/ref, `INTEGRATION_TEST_MODE=true`, `SUPABASE_DB_PASSWORD`가 있어야 한다. 비밀값은 출력·커밋하지 않는다. CA 인증서는 [Supabase Database Settings](https://supabase.com/docs/guides/database/psql)의 인증서를 사용한다.

```powershell
$env:TEST_DB_CA_FILE='<다운로드한 CA 인증서의 절대 경로>'
# 승인된 격리 프로젝트에 신규 RPC만 적용하고 검증
pnpm run test:reservation:db --apply
# RPC 적용 후 재검증: 마이그레이션 실행 없이 테스트만 수행
pnpm run test:reservation:db
```

러너는 `nlzcikoxttenpcflikpd`와 일치하는 HTTPS origin만 허용하고, 그 ref에서 DB 호스트를 직접 만든다. 임의 DB URL이나 Production 대체 연결을 받지 않는다. 연결 검증 실패 시 마이그레이션·테스트 데이터 쓰기 전에 종료한다. `--apply`는 이 새 SQL 파일만 실행하며 기존 테이블 초기화·과거 데이터 정합성 보정은 수행하지 않는다. 이 실행은 Supabase CLI의 migration ledger 등록을 대신하지 않는다.

테스트는 매 실행마다 생성한 UUID의 세션·상품·예약만 사용한다. 별도의 DB 연결 두 개가 실제 잠금을 기다리는지 `pg_stat_activity`로 확인한다. 롤백 검증에는 테스트 판매자의 상품 UPDATE에서만 예외를 발생시키는 일시적 트리거를 사용한다. `finally`에서 트리거와 전용 세션/FK 데이터를 정리하고 잔여 행 수를 확인한다. 검증 실패와 정리 실패를 구분하며, 정리 확인 전에는 최종 통과를 표시하지 않는다.

## Ponytail 재리뷰와 한계

API 호출자, 사용자/관리자 인증, 기존 일정 수정·version 조건, SQL 잠금 순서, 부분 고유 인덱스, 종료 재시도, 만료 호출부, 오류 응답과 테스트 정리를 연결해서 검토했다. 같은 트랜잭션에서 상품 상태를 확인·변경하므로 기존의 분리 UPDATE를 호출하는 우회 종료 경로는 남기지 않았다. 생성 재전송의 다른 상품 예약을 불필요하게 잠그지 않도록 조회만 하며, 같은 상품의 현재 예약은 바깥 상품 잠금으로 보호한다.

재리뷰에서 오류 메시지 whitelist가 객체의 상속 속성을 허용하지 않도록 `Object.hasOwn`을 사용하고 해당 회귀 테스트를 추가했다. 범위 내 남은 필수 수정 사항은 발견하지 못했다. 판정은 **격리 검증된 수정안 준비 완료, 운영 적용 보류**다. 상품 상태를 직접 편집하는 기존 사용자/관리자 상품 API와 외부 service role 쓰기까지 RPC로 전환한 것은 아니므로 임의의 수동 SQL에 대한 전체 DB 불변식을 보장한다고 해석하지 않는다.

- 지연 만료는 기존처럼 최대 100개씩 처리한다. 정확한 시각의 백그라운드 만료 실행을 보장하지 않는다.
- 기존 데이터의 불일치는 자동으로 일괄 수정하지 않는다. 운영 적용 전 읽기 전용 점검 후 개별 조치가 필요하다.
- 실제 HTTP 쿠키 인증부터 DB까지의 연결, 실제 사용자 흐름·운영 트래픽 부하, 장애 중 프로세스 종료/네트워크 단절은 이번 실제 DB 통과 범위가 아니다. SQL 권한 거부와 모의 핸들러 인증 검증을 이 범위와 구분한다.
- 테스트용 REST 키의 401 원인 수정은 이번에 하지 않았다. 향후 HTTP/DB 통합 실행 전 테스트 프로젝트의 publishable/service role 키를 안전하게 확인해야 한다.
- 운영 적용·배포 전이므로 공개 서비스의 기존 위험은 남는다. 다른 감사 항목을 이번에 해결했다고 표시하지 않는다.

## 운영 적용 순서와 복구 방안 — 이번에는 실행하지 않음

1. 운영 연결 ref를 다시 확인하고, 기존 예약/상품 불일치를 **읽기 전용**으로 점검한다. 기존 데이터 자동 해제·수정은 하지 않는다. 필요한 개별 복구는 별도 승인·대상 목록으로 준비한다.
2. 예약 쓰기가 없는 전환 구간을 마련한다. 사용자/관리자 예약 변경뿐 아니라 만료를 실행하는 `/api/session/state`, 예약 GET/POST도 포함한다. 이전 인스턴스의 요청을 모두 끝내고 구버전의 분리 UPDATE와 신버전 RPC가 동시에 쓰지 않게 한다.
3. 신규 SQL만 트랜잭션으로 적용하고 두 RPC의 실행 grant 및 PostgREST schema cache를 확인한다. 일반 사용자 실행 차단과 API 서비스 역할 연결을 확인한 후 새 앱을 전환한다. 기존 테이블·행을 초기화하지 않는다.
4. 새 경로만 동작하는지 확인하고 쓰기를 재개한다. 운영에 테스트 상품·예약을 만들지 않고 오류·충돌과 불일치 조회를 관찰한다. production 설정/데이터 변경은 별도 운영 적용 작업에서 수행한다.
5. SQL 설치 도중 실패하면 전체 DDL 트랜잭션이 롤백된다. 앱 전환 후 문제가 있으면 먼저 예약 쓰기/만료 경로를 멈추고 수정안을 재검토한다. 구버전 앱으로 단순 복귀하면 비원자적 종료 문제가 다시 생기므로 쓰기를 즉시 재개하지 않는다. 추가된 RPC를 유지한 채 전진 수정하는 것이 우선이며, 함수 제거가 필요하면 호출 앱을 먼저 중단하고 해당 두 함수만 제거한다. 상품·예약 행 삭제나 전체 DB 복원은 기본 복구 절차가 아니다.
